# test-fix-loop — 测试修复循环

输入：/test 产出的结构化失败清单。产出：全绿确认，或轮次上限耗尽后的转人工清单。

## 1. 失败归因三分类

| 分类 | 信号 | 处理 |
| --- | --- | --- |
| **断言失败** assertion | 有明确的 expected vs actual；断言消息完整；代码可执行到断言处 | 按业务语义判断是实现错还是测试错；默认改实现，改测试需用户确认 |
| **环境问题** environment | 模块找不到/依赖缺失、端口占用、超时、路径分隔符或大小写问题（Windows 高发）、编码乱码、权限错误、编译/加载错误 | 修环境不碰业务代码：装依赖、清缓存、改配置；把定位证据写进汇报 |
| **真实回归** regression | 失败用例最近没改过、但被本次改动间接破坏（对照 `git log`/`git diff` 判断） | 视为高优先级：先确认「改前也失败吗」（`git stash` 后重跑该用例，做完立即恢复），再最小修复 |

归因证据不足时保持两个假设并行列出，先验证成本低的那条。

## 2. 修复循环（每轮）

<!-- LOOP-RULES-START -->
```json
{
  "max_rounds": 3,
  "rerun": {
    "vitest": "npx vitest run <file>",
    "jest": "npx jest <file> --testNamePattern \"<case>\"",
    "pytest": "python -m pytest <file>::<case> -q"
  },
  "full_confirm": "失败集清零后必须全量重跑一遍确认无连带破坏",
  "escalate": "达上限仍有失败：停止修复，输出未解决清单 + 每项已尝试方案 + 建议交给用户"
}
```
<!-- LOOP-RULES-END -->

1. 对失败清单逐条归因（第 1 节），按 batch 排序：environment 最先（环境不修好，其余结果都不可信）→ regression → assertion。
2. **最小改动**修复：每个被修改的文件必须能对应到失败清单中的用例；不重构、不顺手改格式、不「路过式优化」。
3. 只重跑失败集（`rerun` 表）；失败集清零后**全量重跑**确认（`full_confirm`）。
4. 轮次 +1；仍有失败则回到 1；达 `max_rounds` 上限执行 `escalate`。
5. 每轮结束在会话里汇报：本轮修了什么、归因、重跑结果、剩余失败数。

## 3. 最小改动红线（「零误改」核对）

- 修复完成后逐一核对：改动文件列表 ⊆ 失败清单涉及的文件 ∪ 环境修复清单。多出来的文件必须在汇报中解释理由，解释不了就还原。
- 禁止为通过测试而：删除/跳过测试（`skip`、`xit`、`@pytest.mark.skip`）、放宽断言、改测试期望值——除非用户明确确认测试本身有误，且在汇报中记录用户确认。
- 环境类修复（依赖安装、配置文件）不算误改，但要单独列出。

## 4. 收尾

全绿：汇报总轮次、每轮修复点、最终通过数/跳过数、修改文件清单及对应用例。转人工：未解决清单 + 已尝试方案 + 用户的三个可选下一步（继续加轮 / 只跑某子集 / 人工介入）。
