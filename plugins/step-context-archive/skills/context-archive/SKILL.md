# Context Archive（上下文归档与召回）

本技能是 `/archive` 与 `/recall` 两个命令的行为约定：归档把早期任务块的**原文**
写到项目内的归档文件，对话里只留一行带摘要的 `#STAMP` 索引；需要细节时再按索引取回。
技能负责说清：这些索引行是什么、什么时候必须召回、摘要能不能当事实用。

## #STAMP 索引行语义

```
#STAMP <id> → <归档路径> — 目标：…；关键决策：…；是否完成：…
```

- `<id>`：12 位小写十六进制，标识一个归档块（无法计算哈希时允许 `b` 前缀退化短 id，
  见 `/archive` 规则块）；
- `<归档路径>`：归档文件位置（**项目相对路径**，换机器/移动仓库仍可解析），命名固定为
  `stamp-<id>.md`，内容是块被归档前的**原文**（未经摘要、未经截断）；早期索引行若为
  绝对路径，按其中的文件名在归档目录内定位；
- 摘要部分**只是导航**，不是原文的可靠复述，细节可能失真——**一切以归档文件为准**。

## 三点摘要协议

每个归档块的摘要固定三点，每点一行、前缀依次为：

- `目标：` 当时要解决什么问题（任务来源、动机）；
- `关键决策：` 实际采用了什么方案、改了哪些文件、跑了哪些命令；
- `是否完成：` 已完成 / 部分完成（缺什么）/ 未完成，以及未决项与下一步。

要求：不复述大段日志与代码；保留关键文件路径、命令与数字；三点合计控制在一行到几行。
摘要与归档原文冲突时，以原文为准。

**完成状态必须显式汇报**：归档结束时按块说明"已完成 / 部分完成 / 未完成"，
不允许只给摘要而不交代任务是否完成；未完成任务与未决问题不得因归档而消失。

## 召回纪律

1. 需要历史细节时，读 `#STAMP` 指向的归档文件，再基于**原文**回答；
2. **必须召回**：用户引用历史原话；需要精确的报错全文、堆栈、命令输出；需要被删除或
   被截断的代码片段；需要确认早前决定的依据；某块的"是否完成"含糊或与当前文件矛盾；
3. **不必召回**：话题已切换；信息在当前工作区文件里能直接读到（直接读文件更可靠）；
   用户明确表示不用翻历史；
4. 召回失败（文件缺失、id 非法）时，如实说明失败原因与尝试过的路径，
   **不要**用"原文大概是……"编造；
5. 一次回答尽量只召回所需的最少块，避免把全部归档灌回上下文。

## 归档后的行为约定

- 归档完成后先通读本轮产出的全部 `#STAMP` 行，建立"有哪些历史块、各自讲什么"的整体认知，
  再继续当前任务；
- 摘要只用于导航，**不用于引用**：需要原话、精确数字、完整代码时一律召回；
- 归档目录默认 `.stepcode/context-archive/`；如已纳入版本控制需自行决定
  `.gitignore` 或提交策略（归档是会话级产物，通常不建议入库）。

## 适用与不适用

**适用**：长会话、跨多轮/多日续接的任务、工具输出巨大、需要精确历史引用。

**不适用**：短会话（还没有值得归档的块）；一次性问答；信息可从当前文件系统直接获得
（直接读文件比召回更可靠）；**把归档目录当持久知识库使用**——它面向会话续接，
不是跨项目资料库。

## 相关命令

- `/archive` —— 归档已完成任务块，产出 `#STAMP` 索引行并汇报完成状态；
- `/recall <stamp>` —— 按 stamp 取回归档原文。
